# Approved ARM64 Linux userspace architectural execution (B3.5d/e/f/g)

This experiment executes a reviewed instruction body, using either the embedded
reference or actual generated bytes, with one validated raw `InputData` fragment
per process. It returns actual architectural
state, **not an H-trace**. Its opt-in program transport accepts the exact
reviewed B3.4a image or an explicitly selected MOVZ-immediate-only family. It has no
arbitrary-program loader, PMU access, timer, cache observer,
kernel-module dependency, speculative model, or production executor integration.
Do not extend its command line to accept arbitrary machine code.

B3.5i passed native Ubuntu AArch64 CI on a 4K-page kernel (user-reported):
45 tests, 102 executions/oracle/model matches, five images, and the additional
seq/cond correspondence regressions. For first target runs, use the
[M3 experiment runbook](README.m3-experiment-runbook.md). Cross-compilation,
Unicorn execution, and host mocks do not establish native execution. Fedora Asahi
M3 Pro execution and its memory-protection policy remain unverified.

## Fixed fixture and independent oracle

`arm64_architectural_fixture.S` is assembled by GNU AArch64 binutils. Its 36-byte
read-only object contains B3.4a's 32-byte body followed by `RET X30`:

```asm
cmp x0, #0
b.eq taken
mov x1, #11
b join
taken: mov x1, #22
join:  ldr x2, [x20], #0
add x3, x1, x2
str x3, [x20], #0
ret
```

Tests establish equality to bytes `[12,44)` of the actual generator/assembler/ELF
result from `tests/arm64/asm/contract_slice.asm`. The start/end measurement
placeholders and model exit NOP are omitted, not expanded into kernel macros.
All intra-body branches retain their relative displacements. The assembled
fixture and trampoline have no relocations. Neither loads literals nor calls an
external function. The executable is linked normally; only the fixture's raw
bytes are copied into the new executable mapping.

| X0 selector | Initial main word | Final X0 / X1 / X2 / X3 | NZCV | Main word |
| --- | --- | --- | --- | --- |
| 0 | 7 | 0 / 22 / 7 / 29 | `0x60000000` | 29 |
| 1 | 7 | 1 / 11 / 7 / 18 | `0x20000000` | 18 |
| 2 | 19 | 2 / 11 / 19 / 30 | `0x20000000` | 30 |

The original three cases remain regression inputs, now provided through the
adapter rather than embedded in C. Additional B3.5e cases are:

| Input index | Selector | Initial word | X1 / X2 / X3 and stored word | NZCV |
| --- | --- | --- | --- | --- |
| 0 | 0 | 7 | 22 / 7 / 29 | `0x60000000` |
| 1 | 1 | 7 | 11 / 7 / 18 | `0x20000000` |
| 2 | 2 | 19 | 11 / 19 / 30 | `0x20000000` |
| 3 | 0 | 7 | 22 / 7 / 29 (identical input) | `0x60000000` |
| 4 | 1 | 18 | 11 / 18 / 29 | `0x20000000` |
| 5 | 0 | `2^64-1` | 22 / `2^64-1` / 21 (wrap) | `0x60000000` |
| 6 | `2^64-1` | 5 | 11 / 5 / 16 | `0xa0000000` |
| 7 | 0 | 41 | 22 / 41 / 63 | `0x60000000` |

Input 7 also initializes each remaining main word `i` to `i+100`, for `i=1..511`.
All those bytes must survive execution. Inputs 0/4 have the same stored result
and final main memory but different complete register/flag states. This supported
input-to-complete-state map is injective: X0 retains the selector, X2 retains
the original first word, and the remaining main bytes are preserved. Different
serialized inputs cannot produce identical complete reported state in this
subset; an equal stored word is not asserted to be full architectural equivalence.

X4-X7 start and remain zero. The body reads X0 and X20, writes X1-X3 and NZCV,
loads eight bytes at main, and stores eight bytes at main. Other bytes in the
logical 4096-byte main payload retain their initial values. CMP supplies the final flags; MOV,
ADD, load, store, and branch do not overwrite them. The test's arithmetic oracle
is independent of both native execution and Unicorn. There are no expected
architectural output values in the C runner.

## Approved generated-program admission (B3.5f)

The original `rvzr-b34a-body-v1` policy remains an **exact approved-program loader**,
not a general machine-code sandbox,
an instruction decoder, or a mnemonic allowlist. Only one concrete 36-byte image
is admitted. Random programs, even apparently harmless variations, are unsupported.

`export_approved_program(test_case)` accepts the existing production generator ->
GNU assembler -> ELF parser -> `TestCaseProgram` path used by B3.4a. It checks one
actor/section, the expected measurement/function symbols, ELF64 little-endian
AArch64 ET_REL identity, no segments, at most 16 sections, no nonempty relocation
sections, no compressed sections or extra nonempty allocated sections, and matching
section metadata. It reads at most 65537 bytes and rejects objects over 65536 bytes.
The entire `.data.main` section must equal the reviewed 60-byte template.

The section's name does not make it a runtime data allocation: GNU places these
instruction bytes in `.data.main`. The exporter deliberately extracts its bytes;
it does not use ELF load segments or section permissions to execute an ELF image.
Actor metadata, RCBF headers, `.symtab` labels and relocation metadata are not code.

| Original `.data.main` range | Treatment |
| --- | --- |
| `[0,12)` | Three measurement-start placeholder NOPs, checked then omitted |
| `[12,44)` | Eight actual instructions, copied from the generated ELF |
| `[44,56)` | Three measurement-end placeholder NOPs, checked then omitted |
| `[56,60)` | Model exit NOP, checked then omitted |
| Native `[32,36)` | Append the reviewed `RET X30`; no kernel epilogue or macro expansion |

The resulting approved instruction words are independently matched against
`arm64_architectural_fixture.S` assembled by GNU binutils:

| Native offset | Word (hex) | Instruction and safety property |
| --- | --- | --- |
| 0 | `f100001f` | CMP X0,#0; reads a scalar, sets flags |
| 4 | `54000060` | B.EQ to offset 16; other successor is offset 8 |
| 8 | `d2800161` | MOV X1,#11 |
| 12 | `14000002` | B to offset 20 |
| 16 | `d28002c1` | MOV X1,#22 |
| 20 | `f8400682` | LDR X2,[X20],#0; owned `[main,main+8)`, writeback preserves X20's value |
| 24 | `8b020023` | ADD X3,X1,X2; scalar arithmetic, no address computation |
| 28 | `f8000683` | STR X3,[X20],#0; only data write, preserves X20's value |
| 32 | `d65f03c0` | RET X30 to the trampoline's BLR return address |

Both paths are finite and reach the load/store and return. Moving the body down
12 bytes preserves its internal relative branch displacements. SP, LR, X18,
X19, X20's value and the other ABI-preserved state cannot be clobbered by this
image. No input-derived value supplies an address, control-flow target, or system
register operand. The only indirect branch in the admitted image is the controlled
return; the surrounding trampoline's BLR is also component-controlled.

Opt in with these exact arguments (the old input-only invocation remains valid):

```text
--input-format rvzr-inputdata-raw-v1 --program-format rvzr-b34a-body-v1
```

Stdin is exactly **12324 bytes**: `[0,36)` approved code, `[36,12324)` the unchanged
`encode_input(input_)` result, then EOF. There is no supplied length, entry offset,
actor count, address, path, relocation or permission field. Python composes
`export_approved_program(test_case) + encode_input(input_)`; it does not replace
generated code with the reference constant. Native instructions start at a
kernel-page-aligned mapping base, so all instruction PCs are four-byte aligned.
The 36-byte image fits in both supported kernel page sizes.

C reads into bounded owned stack storage, requires exact size and EOF, and compares
**every received program byte** against its GNU-assembled read-only reference.
It validates input fields too, publishing neither snapshot on rejection. The child
rechecks identity before its data/code allocations, copies **the received program snapshot**
into RW code memory, synchronizes caches, then changes it to RX. The embedded
image is an approval reference in this mode, never a replacement/fallback for
unapproved bytes. Metadata reports `program_source: "approved-generated"` versus
`"embedded-reference"` for the legacy mode. No retry broadens admission.

Python's relocation rejection is an artifact policy. C receives raw bytes, not
ELF relocation metadata; exact byte identity establishes the concrete execution
properties independently. This does not authenticate who produced the bytes or
prove arbitrary ELF metadata trustworthy. All safety arguments rely on the
reviewed reference, trusted executable/trampoline and normal userspace OS/ABI.

| Assurance | What establishes it |
| --- | --- |
| By construction/review | Exact words establish finite internal control flow, scalar-only computation, one bounded data write, preserved ABI-critical values and a controlled return. This proof is specific to this image. |
| Checked dynamically | ELF/template identity in Python; exact packet length, EOF, format, input-field restrictions and full program equality in C; a second program check at execution entry; mapping/publication errors, child exit/timeout, final memory postconditions and architectural oracle/model comparisons. |
| Still unsupported | General instruction/CFG verification, arbitrary programs or paths, relocation application, actor transitions, fault handling, observation-PC translation, cache/PMU tracing, and adversarial-code isolation. Native 16K/M3 compatibility remains unverified. |

Tests reject altered bytes, branches outside the image/self-loops, indirect
branches, SP/LR/X18/X19/X20 changes, unsupported load/store bases/writeback,
privileged-register instructions, incomplete/excess/misaligned packets, ELF/RCBF
containers and unsupported formats. **Malformed program bytes are never sent
to an executing native runner**: negative tests compile the actual C admission
code into a harness whose invocation is a nonexecuting stub. Allocation counters
must remain zero, and both snapshots must remain unpublished. Copy-source tests
check that the admitted received buffer supplies the published bytes.

The native positive regression exports the real generated artifact and runs the
eight B3.5e inputs twice: **16 additional native executions**, each compared with
the independent oracle and the production sequential Unicorn model. Together
with the unchanged B3.5e regression, a successful CI run completes **38 native
executions/oracle comparisons/model comparisons**. Native invalid-program
executions remain zero. The runner does not produce C-traces or H-traces; moving
PCs and removing model macros would require explicit observation-coordinate
handling in a future hardware observer.

## MOVZ-immediate-only family (B3.5g)

The separate opt-in format is **`rvzr-b34a-movz16-v1`**. The old input-only mode
and `rvzr-b34a-body-v1` retain exact-image admission. Python defaults to that old
policy; varying a program never implicitly selects the new format.

### Source audit and concrete policy

`rvzr/code_generator.py:202-244` parses the template, applies passes, prints GNU
assembly, assembles it and populates ELF metadata. `rvzr/arch/arm64/generator.py:64-72`
prints immediate operands; template instructions bypass the memory/undefined-result
instrumentation passes (`:145`, `:214`). `rvzr/arch/arm64/asm_parser.py:120-125`
matches `#` immediates by operand kind. `rvzr/elf_parser.py:226-244` populates
instruction/symbol metadata. Tests reuse those production components with the
existing `tests/arm64/min_arm64.json` subset and **no RANDOM macros**. They only
replace the two literal MOV constants in a temporary copy of the B3.4a template.
A fresh generator is used for each template, avoiding its cached-template behavior.

The subset's MOV-immediate spec at `tests/arm64/min_arm64.json:18-23` misleadingly
describes an imm9 range, with width zero. The template parser does not range-check
that description. This work does **not** establish correct random immediate
generation from that spec. GNU assembly plus concrete byte admission, rather than
the mnemonic or operand-range comment, determines what is executable here.
Tests check parsed destination X1/64-bit/write-only, immediate/read-only, no
implicit flag operands, and exact emitted words. The unchanged production
sequential model (`rvzr/model_unicorn/model.py`, `ARM64UnicornModel._load_input`)
executes each corresponding generated case; no model or generator fix is needed.

For the nine little-endian 32-bit words `w[i]` of the **36-byte** native image:

* Words 2 and 4 (byte offsets 8 and 16) must satisfy
  **`w[i] & 0xffe0001f == 0xd2800001`**.
* All other words must equal the reviewed fixed image above, including RET X30.
* Each variable word therefore is exactly
  **`0xd2800001 | (k << 5)`, `0 <= k <= 65535`**.

Only mask `0x001fffe0`, bits [20:5], varies. `sf=1`, MOVZ opcode, `hw=0`, and
`Rd=1` are immutable: neither W1, MOVN/MOVK/ORR, shifts, another register nor another
instruction form is admitted. See Arm's official
[MOVZ encoding and semantics](https://documentation-service.arm.com/static/67e40f3398aa3c3b6eea6a85)
(MOVZ, page 652). GNU emits the expected MOVZ encodings even at 0 and 65535 in the
tested templates. An alternative MOV alias encoding would be rejected.

This is a fixed-shape family of 2^32 constant pairs, **not** a claim that every
pair was measured. Its safety argument covers the field range by construction:
the constants only supply X1, then scalar addition and stored data. They cannot
change flags, branch targets, instruction count, address operands, SP, LR, X18,
X19, X20 or ABI-preserved registers. The CFG stays `0 -> 4 -> {8,12 | 16} -> 20 ->
24 -> 28 -> 32 -> controlled return`, with no loop. Load/store addresses remain
exactly `[owned_main, owned_main+8)`, with zero writeback; constants cannot become
pointers. Initial memory and selector are still governed by the B3.5e adapter.

The ELF envelope, actor count, symbol metadata and 12-KiB input fragment are
unchanged. Export actual bytes with
`export_approved_program(case, FAMILY_FORMAT)`, append `encode_input(input_)`,
then invoke the same compiled binary with:

```text
--input-format rvzr-inputdata-raw-v1 --program-format rvzr-b34a-movz16-v1
```

No new packet fields exist: exactly 36 code bytes + 12288 input bytes, then EOF.
Python and C independently check the same masks. C checks the selected policy
at admission **and before child allocations**; it copies the received snapshot,
never substitutes the reference. Guarded allocations, W^X, cache synchronization,
ABI trampoline, child deadline, cleanup and memory postconditions are unchanged.
Metadata adds `program_format`; `fixture` continues to identify the shared
`b34a-fixed-body-v1` template, not the exact variable program identity. The test
report separately records each actual image's SHA-256 and constants.

## Restricted input transport and ownership (B3.5e)

The input-only invocation is `--input-format rvzr-inputdata-raw-v1`, with
one **12288-byte** raw actor fragment on stdin, followed by EOF. This tag names
the experiment's restricted transport; it is not a kernel ABI or a new RDBF
version. No automatic format detection is used. All intervals below are half-open
and relative to the start of the raw fragment, not to a runtime mapping base.

| Raw byte range | Meaning | Accepted values |
| --- | --- | --- |
| `[0,4096)` | Main payload, 512 little-endian uint64 words | All byte patterns |
| `[4096,8192)` | Faulty payload | Zero only; no faulty mapping is provided |
| `[8192,8200)` | GPR slot 0, X0 branch selector | All uint64 values, never dereferenced |
| `[8200,8240)` | X1-X5 initial slots | Zero only |
| `[8240,8248)` | NZCV input slot (not X6) | Zero only |
| `[8248,8256)` | SP input slot (not X7) | Zero only; host stack is owned by the trampoline |
| `[8256,8512)` | SIMD initialization | Zero only |
| `[8512,12288)` | Serialized padding | Zero only |

The Python adapter requires the actual one-actor `InputData` dtype, little-endian
payloads, and zero unsupported fields. It returns immutable owned `bytes` equal
to `InputData.save()` output and to the fragment after the 32-byte one-actor RDBF
header/metadata from `save_input_sequence_as_rdbf()`. Existing serializers are
unchanged. RDBF files, multiple fragments/actors, format paths, unknown versions,
truncation, excess bytes and nonzero unsupported fields are rejected by C too.

C's legacy input mode reads at most 12289 bytes into a bounded stack buffer, handles short reads and
requires EOF with a two-second input deadline. Only complete valid input is
copied to a separate stack snapshot, **before any result/data/code allocation or
fork**. Caller must supply a sole-consumer pipe or redirected file and close
stdin; the outer process-group timeout still bounds blocking OS operations.
The snapshot is inherited privately by the execution child, never borrowed from
Python, a file mapping, or external storage. Both buffers have automatic storage
duration, including on rejection. There are no input allocation/free failure paths.

The full main payload is copied to an owned RW page, while remaining bytes of
a 16K data page stay zero. X0 comes from the validated selector bytes; X1-X7 and
NZCV are initialized to zero by the unchanged trampoline. All addresses, SP and LR
are established by the component; code identity is fixed by its reviewed reference.
Scalar data may numerically resemble
an address but is never used as a pointer. Main data is never copied into code.
This is not a general input adapter for arbitrary generated/boosted inputs:
nonzero excluded fields are rejected, not silently dropped.

## Safety and lifetime review

* Only Linux little-endian AArch64 is accepted for the actual executable. Runtime
  page sizes 4096 and 16384 are supported; other sizes fail explicitly. Logical
  main remains 4096 bytes. Each private allocation reserves three kernel pages:
  `PROT_NONE` guard, payload page, `PROT_NONE` guard. At 16K, trailing bytes of
  the middle data page are padding, **not another logical input region**.
  Guards do not protect individual subpage logical boundaries. This is not
  activation of Revizor's passive candidate 16K sandbox profile.
* Data is RW and never executable. Code goes from inaccessible to RW for the
  copy, through GCC `__builtin___clear_cache`, then RX. No RWX request, writable
  executable alias, fixed virtual address, private PTE update, or protection
  fallback is used. `READ_IMPLIES_EXEC` is queried and rejected, not changed.
  A denial of executable memory or cache publication is a failure.
* The ABI trampoline initializes X0-X7 and NZCV and sets X20 to owned main memory.
  Other caller-saved registers are not general-purpose input state; the fixed
  body does not read them. X19 retains the result pointer. FP/LR and X19/X20
  are saved/restored with a 32-byte frame; SP remains 16-byte aligned. X18,
  X21-X28 and SIMD are untouched. The fixed body leaves SP, X19, X20 and LR
  intact, so RET reaches the trampoline, which captures X0-X7 and NZCV before
  restoring host state. There is no sandbox-stack switch or signal recovery.
* The native fixture's only data write is `[main,main+8)`. Trampoline writes
  target its own 32-byte frame and its C result object (80 bytes, offsets checked
  by `_Static_assert`). It never writes executable memory after publication.
  Tests also emulate the real trampoline with sentinel X18-X29, LR/SP and Q8-Q15
  to check preservation; this supplements source inspection, not native evidence.
* Each accepted input gets a fresh child and fresh data/code reservations. The parent owns
  one small shared result mapping, prefaulted before fork, and reads it only
  after a successful wait/exit and completed cleanup. Both reservations are
  released even after partial setup failure. Failed releases are failures;
  child process exit releases any residual mappings. No retry follows failure.
* Parent wait uses a 2-second monotonic deadline and kills/reaps only its owned
  child on timeout. Signals, nonzero exits, setup errors and incomplete results
  are failures. There is no instruction-fault continuation. Parent termination
  by an external agent is outside this internal deadline; use the outer timeout
  below for process-group cleanup. A process stuck indefinitely in kernel exit
  cannot be given a strict userspace time bound.
* This is reviewed trusted code, not an adversarial-code sandbox: a child still
  has process credentials and inherited descriptors. No safety argument here
  permits arbitrary or unreviewed instructions, SP/LR corruption, actor transitions,
  faults, privileged instructions, or kernel-like fault/permission semantics.

The ABI obligations follow [AAPCS64](https://github.com/ARM-software/abi-aa/blob/main/aapcs64/aapcs64.rst).
Cache publication uses GCC's documented
[`__builtin___clear_cache`](https://gcc.gnu.org/onlinedocs/gcc/Other-Builtins.html),
rather than a guessed cache-line stride. Linux
[`mprotect`](https://man7.org/linux/man-pages/man2/mprotect.2.html) operates on
kernel-page-aligned mappings. BTI/PAC/SELinux or other policy changes on a future
target require validation; this utility does not disable system protections.

## Native build, execution and CI

From the repository root on native AArch64 Linux, without sudo for execution:

```bash
python - <<'PY'
from pathlib import Path
import numpy as np
from rvzr.tc_components.test_case_data import InputData
from tools.arm64_userspace_input import encode_input
input_ = InputData(1)
input_.view(np.uint8).fill(0)
input_[0]['gpr'][0] = 0
input_[0]['main'][0] = 7
Path('architectural-input.raw').write_bytes(encode_input(input_))
PY
gcc -std=c11 -O2 -Wall -Wextra -Werror \
  tools/arm64_architectural_smoke.c tools/arm64_architectural_fixture.S \
  -o /tmp/rvzr-architectural-smoke
timeout --signal=TERM --kill-after=2s 10s \
  /tmp/rvzr-architectural-smoke --input-format rvzr-inputdata-raw-v1 \
  < architectural-input.raw > architectural-state.jsonl
# Check the exit status before using output; preserve partial output on failure.
```

Successful stdout has three JSON Lines: metadata (kernel, page size, fixture
and input-format identity), one `architectural_state`, and a final `complete`
record with `cases:1`. The `input` ordinal is always zero within this process;
external campaign ordering is the caller's responsibility.
Each state records input identity, X0-X7, NZCV, return-point SP modulo 16,
historical data/code base addresses and `main_hex` (all 4096 bytes). Addresses
have already been unmapped when printed; they are diagnostic values, not live
allocation handles. No observation bitmap or trace encoding is synthesized.
Output is under 10 KiB. Any failure has a nonzero exit; ordinary caught failures
emit an `error` JSON record with stage, errno, signal, timeout and child exit.
An architectural-state record alone never implies successful completion. Output/pipe failures may
prevent an error record; always check exit status and the final complete record.
Parse integer fields without floating-point conversion: inputs/results can include
`UINT64_MAX`.

The existing **Verify fixed ARM64 userspace architectural execution (no kernel
module)** step in the existing `arm64-baseline` job runs:

```bash
set -euo pipefail
test "$(uname -m)" = aarch64
gcc --version
RVZR_REQUIRE_NATIVE=1 python -m unittest \
  tests.unit_arm64_userspace_execution \
  tests.unit_arm64_location_correspondence -v
```

No CI changes or new dependencies are needed for B3.5g. It uses the already
installed build-essential/binutils/Python dependencies. The
native test compiles the program with the flags above, checks the generated ELF
body before fixture execution, runs the three legacy inputs and eight new inputs
twice (**22 native fixture executions, 22 oracle comparisons, 22 sequential-model
comparisons**). It separately rejects **16 malformed payloads and 4 unsupported
argument/format requests** without executing the fixture. No arbitrary fuzz-generated case is
sent to the native component. The additional approved-program test runs 16 more
executions as described above; the new MOVZ16 family adds 64. Missing native execution
is an error in CI.

On x86-64 WSL2 use `binutils-aarch64-linux-gnu` and the same unittest module,
without `RVZR_REQUIRE_NATIVE`. The three actual native execution tests skip.
`RVZR_ARM64_BINUTILS_PREFIX` can select an extracted cross-binutils installation.
Host tests include actual C input-reader/admission checks, production byte-parity
and sequential-model checks, mocked allocation/protection/release failures, and
owned-child exit/timeout checks. Mock invocation never executes any fixture bytes or produces
architectural measurements. Its C reference header is generated temporarily from
the actual GNU-assembled fixture, not a zero-filled replacement. 4K/16K arithmetic simulations do not verify native
mapping permissions. The fixture and ABI emulation use actual assembled bytes.

## Before future executor integration

Reuse the reviewed fixed fixture, runtime-page mapping mechanics, code publication,
bounded-child handling and architectural oracle unchanged on Fedora Asahi for
an initial test. Record its actual kernel/page size; do not infer compatibility
from macOS or Ubuntu. The fixed program needs no timer/PMU or CPU affinity.

Keep generation, `TestCaseProgram`, fixed `InputData` serialization, boosting,
contract model and analyser. A future loader needs an explicit supported subset
and validator, bounded relocation/exit translation, broader input-to-register and
memory semantics, preparation/allocation identity, and consistent model addresses.
Faulty pages, multiple actors, arbitrary pointers, host-ABI clobbering, faults and
speculation-sensitive instrumentation need separate safety designs. The existing
kernel's safety blockers remain unchanged.

An architectural-state result can support a later real architectural mismatch
check; it cannot serve as a cache HTrace. Before implementing `Executor.trace_test_case`
for relational leakage testing, independently validate a physical observer and
its noise/repetition/affinity behavior, define its real HTrace representation,
and synchronize model/hardware preparation. No fuzzer, factory, HTrace or analyser
integration is implemented here. This experiment establishes neither a cache
leak nor a Spectre vulnerability.
